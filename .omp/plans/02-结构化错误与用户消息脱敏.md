# 目标

1. Application 对可预期失败返回稳定的 `FailureKind`/状态和安全公开描述；错误分类只按类型或枚举，不按消息字符串解析、比较或猜测。
2. 原始异常对象只在注入的 `ILogger` 边界记录，日志字段经过集中脱敏；Application 结果、UI 状态、通知、runner 失败输出均不得包含异常原文、完整响应或敏感路径。
3. App 集中把稳定失败类别映射为中性、可行动的简体中文文案，例如“请求超时，请稍后重试”“需要重新绑定凭据”“配置未切换，OMP 未启动”“配置已切换，但启动失败，请检查工作目录”；文案不泄露 Provider 凭据、URL query、Authorization、Cookie、私密路径或内部异常。
4. 清除所有用户可达的 `Exception.Message` 直显路径，清除 `SwitchAndStartOutcome.Error`/刷新 `FailureMessage` 的不受控传播；保留足够的结构化类别、ProviderId（仅在安全允许时）和阶段信息供 UI 和日志定位。
5. 删除“已验证浏览器请求指纹”误导文案，并将凭据绑定成功明确表述为“已保存/已绑定到安全存储；供应商有效性须由价格查询结果确认”，不声称认证成功或指纹已验证。
6. 维持既有不变量：刷新单站失败不覆盖旧快照；失败旧快照只可手动选择、不参加自动推荐；配置切换失败不保存且不启动；配置切换成功后启动失败不回滚已切换配置；用户取消仍保留取消语义；不自动切换 Provider。

   - 刷新失败类别、取消、超时、认证失败、旧快照和推荐资格；OMP 配置失败/启动失败/已有进程；SiteEditor 探测失败和凭据保存事实均可由类型/状态和固定文案断言，不按消息文本分类。
   - 全仓库无“已验证请求指纹”及同义误导文案，且绑定凭据不再声称供应商认证成功。
5. 证据记录必须包含场景、实际命令、退出码、关键 `passed` 输出、隔离 data/OMP root、未执行项及原因、真实数据/凭据/Provider 未触及、应用关闭和残留进程检查。若验证失败，修复根因后从受影响级别重新串行验证；不得降低断言、跳过敏感样例或发布。
6. 目标—证据闭环必须逐项记录：目标 1（结构化错误契约）由静态检查确认所有失败结果仅含稳定 kind/status/安全描述、runner 断言分类不依赖消息；目标 2（异常与 synthetic secret 全链不泄露）由静态搜索、各层 runner、隔离 smoke 以及对日志/stdout/stderr/JSON/备份/临时文件的敏感样例扫描共同证明；目标 3/4（唯一 UI 映射且无 Exception.Message 直显）由 App runner 断言 `PriceRow.Issue`、`StatusText`、通知和 MessageBox 文案及静态调用链证明；目标 5（凭据文案不误导）由 SiteEditor 映射断言和全仓库文案搜索证明；目标 6（快照、推荐、切换、取消不变量）由 Refresh/Application/Omp runner 与隔离 smoke 的状态和副作用断言证明。每项必须记录实际命令、退出码和关键通过证据，不能以 build 成功代替行为证据。
7. 执行者在全部适用验证结束后必须明确回答：背景问题是否消除；目标 1 至 6 是否逐项达成；是否具备自主验证充分证据。只有三项均为“是”，且错误契约、脱敏链路、固定 UI 文案和既有不变量均通过，才允许把本文件第 3 行从 `open` 更新为 `closed`；任一项为“否”、失败或证据不足，必须保持 `open`，并记录具体阻塞/未通过项和影响范围。
8. 自动 runner 无法证明 WPF 视觉呈现、控件布局或所有 MessageBox/对话框路径时，不得笼统写“请人工验证”。在关闭状态前由人工验收：使用隔离临时 data/OMP root 和 synthetic（非真实）输入启动应用，逐一触发 MainWindow 刷新失败、配置切换失败、启动失败、未知异常、取消，以及 SiteEditor 探测失败和凭据保存成功路径；操作为观察 PriceRow、状态栏、通知、MessageBox 和 `_probeResult` 的实际显示文本。期望结果是文案与稳定 kind/status 一一对应、可行动且不含 synthetic token、URL query、Cookie、Authorization、私密路径或“已验证请求指纹”；风险是无头 runner 可能只验证绑定值而遗漏遮挡、截断、错误控件或残留旧文案，未验原因须记录具体未覆盖路径。若 App runner、隔离 smoke 和静态检查已覆盖这些可观察文本且人工路径不存在，则明确记录“无需人工验收”。

# 为什么选择此技术路线

将稳定失败类别留在 Application、将安全公开描述作为结果契约、将原始异常限制在 ILogger、再由 App 统一映射用户文案，符合既有分层：Application 不依赖 WPF，App 不重复业务判断，Infrastructure 只负责外部错误边界。这样错误分类不依赖不稳定供应商消息，UI 不会被异常原文或路径污染，runner 可以直接断言类型、状态和脱敏不变量。

采用 clean cutover 删除旧字符串字段和直显路径，而不是保留兼容 alias，可避免调用者继续偷偷依赖 `Exception.Message` 或 outcome.Error；保留既有状态转换和副作用顺序，则不会把安全修复误变成 composition root、SiteEditor Command 或 OMP 生命周期重构。合成敏感样例覆盖 token、URL query 和私密路径，能证明“安全描述”在异常、日志、UI 和 runner 输出的完整链路上成立，而不需要真实 Provider 或真实凭据。

# 注意事项

- 不得把异常消息先放入结果/日志再“后处理”；脱敏必须在首次记录和首次跨边界返回前完成。不得记录完整 URL、query、Authorization、Cookie、token、响应体、命令行、环境变量或真实私密路径。
- 不得以消息字符串判断认证、超时或启动失败；`FailureKind`/status 是唯一程序协议。复杂计费、供应商错误和未知异常无法确定时必须明确失败，不得猜测或静默降级。
- 不得在本计划中迁移 composition root、重写 SiteEditor Command、迁移凭据 root、添加 CI 入口、修改发布脚本或执行 publish；这些属于 01、03、04、05、06、07 的明确边界。不得为“方便”新增平行错误服务、全局服务定位器或跨层引用。
- 不得把 ProviderId、模型名或 URL 主机默认视为安全；逐字段核实是否可能包含凭据/个人信息，必要时只显示稳定的受控标识。用户可行动文案只能提示重试、重新绑定、检查配置/工作目录或查看隔离日志。
- 不得将旧快照失败状态重新标记为成功、权限已验证或可自动推荐；不得因隐藏原文而吞掉异常、自动重试、自动切换或改变取消语义。
- 回滚边界：若新结构化契约导致受影响 runner 或隔离 smoke 失败，回滚仅限本次错误契约/映射/脱敏改动，保留已有安全日志要求和不变量；不得恢复 `Exception.Message` 直显、原始 Error 传播或“已验证请求指纹”文案。若涉及持久化或外部 API 兼容问题，停止 clean cutover 并先由 07 定义迁移策略，不留下双路径。
- 正式发布不是本计划验收项；只有明确发布任务才可按 `rule://build-release` 进入 publish，并且发布脚本质量改进只能验证脚本本身，不能借此执行正式 publish。
